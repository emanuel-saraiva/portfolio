01 / Professional project · Financial reporting · Anonymized

Enterprise Data Lake & Analytics

From heterogeneous Excel files to reusable Delta tables and a Power BI report on annual consumed amounts across three entities: an end-to-end analytics workflow built with Microsoft Fabric, notebooks, dbt, Fabric Pipelines and Direct Lake.

Microsoft FabricOneLakeLakehousepandasPySparkDelta LakedbtFabric PipelinesPower BIDirect Lake
The problem

Different source files. One reliable reporting workflow.

Financial datasets for three entities arrived as Excel files with different structures, naming conventions and data types. They needed to be prepared, transformed and served consistently for annual spending analysis, without embedding the preparation logic in a single Power BI report.

What was delivered
  • Preserved raw files in OneLake
  • Bronze and staging Delta tables
  • Notebook → dbt orchestration
  • Direct Lake semantic model and Power BI report
  • Report access through a fixed identity
Confidentiality. Project context, identifiers and examples are anonymized. The Power BI report image preserves the original layout but replaces supplier names, tax identifiers and financial amounts with fictional data. The SQL snippet is illustrative rather than copied from production.

02 / PREPARE

Ingestion and technical normalization

Each original Excel file was retained in Files/raw. Fabric notebooks used pandas for profiling and preparation, before conversion to PySpark and persistence as Bronze Delta tables.

ProfilingInspect before transforming

Checked nulls, duplicates, inferred types and columns containing mixed values.

IdentifiersPreserve semantics

Normalized names and handled tax identifiers as strings rather than numeric measures.

Decimal valuesFail explicitly

Converted European decimal formats such as 56347,50, raising errors for invalid conversions.

These checks addressed concrete issues discovered in the sources. They were not a formal enterprise-wide data governance or data quality program.

03 / MODEL

SQL transformations with dbt

dbt declared Bronze tables as sources and produced physical staging Delta tables. One source contained separate monetary columns for three years; a staging transformation reshaped these columns into a consistent year-and-amount structure.

-- Simplified example, not production SQL
select tax_id, 2024 as year, amount_2024 as amount
from {{ source('bronze', 'source_example') }}
union all
select tax_id, 2025 as year, amount_2025 as amount
from {{ source('bronze', 'source_example') }}
union all
select tax_id, 2026 as year, amount_2026 as amount
from {{ source('bronze', 'source_example') }}
1,034 source records → 3,102 staging records. Three yearly rows were produced per original record. The redundant source total column was excluded from the reshaped result.
04 / OPERATE

Orchestration with Fabric Pipelines

Processing was organized by source. After an Excel file was placed in raw storage, its pipeline ran the associated notebook, then the matching dbt transformation only if the notebook succeeded.

During implementation, a notebook activity failed because of an explicit connection configuration involving Workspace Identity. Removing that connection setting resolved the activity issue. The initial upload of source files remained manual.

05 / SERVE

Power BI, Direct Lake and secure consumption

Staging Delta tables were surfaced through a Direct Lake semantic model and consumed in a Power BI report. The report supports annual financial consumption analysis across three entities, with distinct report tabs for FCT, FCCN and ANI.

The business-facing view includes supplier, tax identifier, procurement procedure, date and amount including VAT. Filters for supplier, procurement procedure, tax identifier and year allow report users to focus on relevant spending records.

Initially, SSO caused OneLake read-permission errors for some report viewers. The final access pattern associated the semantic model with a cloud connection using Workspace Identity as a fixed identity, and distributed report access without requiring consumers to become Viewer members of the technical workspace.

06 / THINK

Engineering decisions and trade-offs

  • Why a Lakehouse? To retain the source files and combine Spark processing, Delta tables and Direct Lake in one Fabric environment. A data warehouse could also support separate structures; flexibility was not exclusive to the Lakehouse.
  • Why separate Bronze from staging? To keep technical type and schema handling distinct from SQL-based analytical reshaping.
  • Why physical dbt staging tables? To produce Delta tables suitable for the chosen Direct Lake serving approach rather than depending on ordinary SQL views.
  • Why source-specific pipelines? To make notebook and corresponding model execution explicit for each input.
  • Why fixed identity for reporting? To grant report access without distributing technical workspace privileges.
07 / IMPACT & NEXT

Outcome and what I would improve next

The delivered solution connected heterogeneous Excel files to profiling, Bronze Delta, dbt staging, orchestrated execution and a Direct Lake Power BI report with an appropriate consumer-access model.
